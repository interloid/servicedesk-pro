## Results

Thresholds are starting targets, not agreed SLOs: under 1% failed, p95 under 1,500 ms for staff and portal, under 800 ms for signed-out pages.

| Load    | 10, held for 3 min         | 2,252    | 0%     | 61 ms     | 74 ms      | 11 ms          | 0       | Pass   |

Spike latency looks good only because a redirect to sign-in is fast and is included in those figures. Judge that run by its failure rate.

**Where failures begin:** in a second stress run with timestamps (29,661 requests, 42.7% failed), the first failure came about 2 minutes in, at roughly 39 requests/s, estimated from the stage timings. They began abruptly, at about 14 per second, rather than building up gradually. The load profile held 10 requests/s with none. The test can't separate rate from accumulated connection churn, so read this as "somewhere between 10 and 39 here", not as a fixed limit.

## Findings

### LOAD-001: an Auth error signs a valid user out of the page

`src/proxy.ts` calls `supabase.auth.getUser()` and ignores the returned error, so any failure leaves `user` null and looks the same as having no session. A signed-in user is then sent to `/{tenant}/login` with a 307.

Evidence from one spike run: Auth returned 500 on 1,414 of 5,511 `/user` calls, and k6 saw 843 redirects to sign-in on the requests it logged. The app logged no errors for this, so **nothing would alert on it.**

This is in the application code, so it applies on any environment where Auth has a bad moment. How often it would happen in production is unknown.

Not fixed. Options need a decision, because this code is a security gate: for example, show a retryable 503 when Auth fails with a server error, while a real "no session" answer still redirects.

### LOAD-002: Auth and the database saturate before the app

The proxy makes an Auth call on every request, including RSC navigations. Local Auth failed with `failed to connect to host=supabase_db_servicedeske2e ... dial error`.

| Stress minute | Auth CPU | Database CPU | Node CPU |
| ------------- | -------- | ------------ | -------- |
| 2             | 17%      | 49%          | 16%      |
| 3             | 58%      | 90%          | 34%      |
| 4             | 94%      | 169%         | 26%      |
| 5             | 268%     | 335%         | 43%      |
| 6             | 343%     | 354%         | 109%     |

CPU figures are 10-second samples averaged per clock minute, and clock minutes don't line up exactly with stages. 100% is one core.

**Update, same day:** the dial errors are a limit of the local stack, now confirmed. Each Auth request opens a new database connection, which then sits in `TIME_WAIT`. The Auth container reached 18,647 of these against about 28,000 available ports. With a wider port range and `tcp_tw_reuse=1` applied, a full E2E run went from 40 to 142 dial errors down to 0.

So the failure point of about 39 requests/s above measures this local limit, not the app. All the k6 runs here predate the change, and **they should be rerun**. The per-request Auth call exists in every environment, and so does LOAD-001. Reading the claims locally with `getClaims()` could remove the call, but a revoked session would then keep working until its token expires, so that is a security trade-off.

### LOAD-003: REST calls fail at the top of the stress run

The app logged 428 `[portal] tenant lookup for "seed-cedar" failed: TypeError: fetch failed`, plus 20 `Couldn't count SLA tickets` errors. No error screen was seen by the k6 checks. This was only at extreme load, on one Node process and local Kong, so treat it as low priority until it is reproduced at a realistic rate.

### LOAD-004: pages that exist answer 404 under stress

In the second stress run, 774 requests got a 404 on pages that exist, across the portal (421 of the top entries) and staff pages. It started at low volume alongside the first sign-in redirects and grew as load increased.

Portal cause, traced: `getPortalTenant` (`src/features/portal/services/portal.service.ts:205`) returns `null` when the lookup fails, which is the same answer as "no such workspace", and the portal layout then calls `notFound()`. The app logged 491 of these lookup failures. A customer would see "not found" for a real workspace during a database or network blip.

Staff pages: `tenant-resolver.ts:165` follows the same return-`null` pattern, and 4 of its lookups failed in the log. That doesn't account for all the staff 404s, so the rest are untraced.

Like LOAD-001, this reports a temporary failure as a definite answer. Not fixed.

## Next steps

0. Rerun `stress` and `spike` on the stack with the wider port range, for a real failure point.
1. Decide how to handle LOAD-001.
2. Make temporary lookup failures distinct from "not found" (LOAD-004), and trace the remaining staff 404s.
3. Add write traffic and more data. 215 tickets will flatter every list and report query.
4. To test hosted infrastructure, use a separate staging project, with Vercel's and Supabase's rules and a warning to both checked first. Never production.
